## 2. B1：只读判别与七类现场

### 2.1 路径与证据清单

约定 `H = Path.home()`，`R = H/.agents-group`，`C = H/.local/share/agent-group-memory`(2026-10-30 用户裁定:产品代码独立落位并版本化,见 §11)，`V = R/var/registry.json`。支持平台仅 macOS；Windows/Linux 本期拒绝生产写入，夹具可测试纯逻辑。

判别阶段包括 import/help/check/预览：不 mkdir、不拿锁、不写日志/缓存/备份、不创建执行器目录；Python 入口禁字节码持久化。逐项观察并在内存报告路径、类型、可读性和指纹：

1. R、父目录、目标目录是否真实目录；V、旧产品账本和受管入口是否普通文件，是否有 symlink 父路径、设备/FIFO/socket、权限错误。R 为 symlink、特殊节点、不可读或身份不明即异常。合法 Skill 链接按 §3 另处理，不能因其存在便把整个现场认作异常或首装。
2. V 的原始字节、重复键、严格字段/schema、`product_id`、三版本、安装 ID、完成状态、当前代码清单及其来源；不是“JSON 能读”就有效。
3. R/var 下安装/迁移/恢复标记、锁、暂存目录；R/backups 下本产品 manifest、提交/回滚记录；R 同级的本产品 bootstrap 操作目录。未完成或无法解释的标记先阻断，完成的历史备份不是中断。
4. C 的 `SKILL.md`、`scripts/agm.py`、`scripts/agm_core/`、产品 Git 来源/提交及发行清单；不以目录名孤证认定产品身份，但产品代码存在而 V 缺失已足以排除“确认无痕迹”。
5. 三家用户入口中的 AGM 受控 marker、本产品 Skill 投影，以及由本次显式安装源定位的 `scripts/registry.json`、`.agm.lock`、`backups`。只查已知路径和批准的旧来源，不全盘扫描。
6. 旧 M2/M3 账本须通过 schema v1 的全部字段、交叉引用、消费者、授权证据和 created manifest 校验，并与明确的产品代码来源关联；v0 `manage/sync/project_manage` 的散落状态不能当 M2/M3 台账。

“已确认无产品痕迹”必须是：上述可枚举位置全部可检查，V/本产品代码/投影/marker/事务/迁移标记/旧产品账本均不存在；R 中存在的旧脚本及状态已列为 v0 排除项，不能冒用产品 schema。保留目录、README、`memories/MEMORY.md` 等用户文件不单独构成产品痕迹。无法读、无法定来源、有未知 var 内容，均不满足这个条件。此结论只表示本次检查范围内无痕迹，不宣称证明历史上从未安装。

### 2.2 无痕迹时的显式身份确认

R 不存在、或真实 R 完全为空且无外部产品证据，走全新；R 非空、无产品痕迹且内容可完整枚举，只能成为 v0 候选，不能自动导入。

预览必须显示 R、观察清单摘要、候选内容清单/总指纹、排除项、快照/目标及准确冲突，提示：

> 未发现可核验产品痕迹，但不能排除台账及痕迹被删除。请确认这是 v0 手工目录，并批准按本计划一次复制并入；若曾安装本产品或无法确认，停止，先找回台账/恢复材料。

交互由用户明确选择“确认 v0 并按此清单复制”或“停止/恢复”。非交互只接受与计划绑定的批准 envelope：`legacy_identity = confirmed_v0`、`source_tree_sha256`、`operation_id`、确认时间和真实确认来源；参数名、目录名、一次安装请求或 Agent 推断不能代替确认。未答/否认/不确定返回待确认或恢复诊断，零写入。确认曾装产品后即使无痕迹，也不得伪装 v0：只走异常恢复，找不到历史材料时保持停止，不合成历史授权或 created。

### 2.3 七类路由表

按“异常/中断 → 未来/不支持 → 有效产品 → 空/v0”优先级；台账与 v0 同在时按产品升级，内容导入是独立获批子计划，不能抹掉旧账。

| 现场 | 判定与通道 | 批准后写范围 | 原件位置 | 恢复动作 |
|---|---|---|---|---|
| 空（R 不存在或完全空） | 无外部产品证据 → 全新安装 | R 标准结构、受管代码、已选 installed 用户入口/产品 Skill、bootstrap 操作目录 | 先前不存在；既有外部入口有逐文件 before 备份 | 按 manifest 逆序撤本次创建/改动；只删本次创建且仍空的目录 |
| v0 | §2.1 无痕迹 + §2.2 明确确认 → v0 存量复制 | 快照/manifest、标准结构、批准导入目标、代码和 installed 接入；新索引置换单独列项 | 原非冲突文件原地；被置换的旧索引逐字节留快照及 legacy 主题；旧脚本/状态/mcp 原地 | 回滚恢复旧索引/入口及受管目标，保留快照；重新规划须新确认，不重复导入 |
| 有效旧版 | 可验证 schema v1 M2/M3，或支持的 M4 已安装旧版 → 升级 | 新台账/迁移材料、受管代码/机制、确需接入对象 | 旧账原始字节、旧代码、旧 manifest 归 §6 档案；用户内容原地 | §5/6 恢复单一旧版或完成本次新版本；不退回首装 |
| 同版 | 有效完成台账，三版本/来源清单吻合 → 升级通道中的幂等分支 | 无变化则零写、无锁/备份/时间戳刷新；新 Agent 接入须有差异计划 | 原地；有差异时备份实际写项 | 漂移即异常停止；合法补装按事务回滚 |
| 未来版 | 任一不支持的更高 schema/结构/代码版本，或无白名单转换 → 异常零写入 | 无 | 全部原地 | 使用能读该版本的安装器；禁止降级、删除台账或复制 v0 |
| 坏台账 | 损坏、重复键、缺字段、类型冲突、身份矛盾、缺 created 证据、双账冲突 → 异常零写入 | 无 | 原地，不在诊断中“备份坏账” | 提供预先存在的匹配备份及独立恢复计划；不自动空账重建 |
| 中断残留 | 未完成 manifest/锁/暂存，或台账完成但提交收尾未闭合 → 异常零写入 | 普通安装无写 | 所有残留原地 | 显式恢复入口核对 §5.3 后继续/回滚；不自动删锁，不重新识别为 v0 |

未来版本是拒绝出口，不是可写升级。有效旧版但缺转换也拒绝。锁持有者活跃时报告忙；无法证明已退出也不清锁。发现坏账不沿用 M2 enable 的空账重建分支：机器级账本先恢复为可信完成状态，项目层才可另行重新确认授权。

## 3. B2：v0 复制、冲突与一次性

### 3.1 源、目标与原件

`op = UTC YYYYMMDDTHHMMSSZ + '-' + UUID`，不靠时间戳保证唯一。预览先列每个路径，获批才创建 `H/.agents-group-install-<op>/`（0700，同文件系统、非 symlink），内含固定恢复工具、before 材料、计划和 journal。这个同级目录使第一笔写入也可追踪；残留会阻断下一次普通安装。

v0 内容快照最终位置为 `R/backups/v0-<op>/source/`，包含且只包含批准的 `memories/`、`references/`、`skills/` 内容，不递归 R 自身，不读写 v0 mcp/脚本/散落状态。快照先在 bootstrap 目录完成并逐文件核验，再由同一操作移动到最终位置；移动 intent/前后位置记 journal。快照根包含 `source-manifest.json`，相对路径、节点类型、模式、文件长度及 SHA-256、链接原始文本及其哈希、目录清单组成排序规范化总指纹。快照完成后只读、不再作工作区；不宣称抵御同用户恶意修改，使用前仍核对指纹。

R 中不冲突的 v0 文件原地保留并与快照逐字节比对，登记为内容复用；缺失目标从快照复制。新结构绝不以仍在变化的 R 为读源。替换旧索引前须证实快照完成；每次写前重核对应原件，提交前复核来源清单：未改项仍须等于 before，本次索引等已批准改项须等于 after，本次新增目标从枚举差异中按精确清单扣除；其他新增/修改/缺失均为源漂移。任何源漂移均停止/回滚，不能以快照已有为由覆盖用户刚写的内容，也不能将本次合法写入误报为源漂移。

旧脚本、状态、mcp 原件不迁移、不删除、不运行、不接管；仍在原路径。新 mcp 目录不存在才创建为空，已存在则只报告“v0 mcp 原件保留、未纳管”，不清空。旧管理器能否理解新索引不作兼容保证；安装预览必须说明不可并发运行旧同步/管理写操作。旧脚本将来重新写本产品目标时按漂移处理，不能用兼容为名改旧源码或创建重定向。

### 3.2 同名 MEMORY 与相对链接

旧 `memories/MEMORY.md` 原始字节保存为 legacy 主题，保留 basename `MEMORY.md`，不改正文、不蒸馏。活动路径固定为：

`R/memories/legacy-v0-<op>/memories/MEMORY.md`

为保留相对链接上下文，`legacy-v0-<op>/` 镜像快照的完整三目录布局（memories/references/skills），而非只孤立搬一个文件；这是只读原文阅读包，不是第二套运行时或 Skills 安装源，不投影其中 Skills。这样原文 `./主题.md`、`../references/operations.md` 等仍到同一包的同字节目标。新 `R/memories/MEMORY.md` 仅写简短索引，链接 `legacy-v0-<op>/memories/MEMORY.md`；≤200 行且≤25KB。根级其他 v0 memories 主题、references、skills 保持既有位置，避免旧脚本和既有引用突然失去原目标。

预览须列新索引、legacy 包和额外复制量。所有可解析本地 Markdown 链接按来源/目标分别核验，URI/锚点不当作文件复制。来源本已失效的链接报告“原有失效”而不修改；因本次布局新产生的断链阻断提交。绝对路径、越出三目录的相对链接只保留文本、不自动复制外部内容；若原目标仍原地且可核验，报告仍依赖原现场，不能宣称 legacy 包独立可搬移。无法保住来源中原本可用链接的场景先停，另取具体处置批准，不篡改原文。

### 3.3 冲突与链接处置

| 来源/目标 | 处置 |
|---|---|
| 目标缺失、来源普通文件 | 从快照逐字节复制，核验长度/哈希，保留允许的普通权限；不传播 setuid/setgid |
| 同路径同类型同字节普通文件 | 原地复用，来源是 v0 用户内容，不产生产品删除权 |
| 同路径异字节，或文件/目录/链接类型不同 | 全计划先停并展示 before/after 指纹；不按 mtime 选、不覆盖、不拼接；解决现场后重新预览 |
| 旧根索引与新索引 | 仅按 §3.2 明示置换，原文同时有快照和 legacy 阅读包 |
| 目标 `legacy-v0-<op>` / 快照名已存在 | 同 op 走恢复核验；不同 op 或无可信 manifest 即冲突，不加后缀绕过 |
| v0 `skills/agent-group-memory` 已存在 | 即使同字节也不自动追认受管代码；若是产品痕迹先按 §2 重判；独立 checkout/异源/dirty/普通复制目录均停止，另批准保全/腾位后再预览，不自动接管或覆盖 |
| 待升级的可信受管产品代码 | §5 的产品升级，不套用“用户内容不动”；漂移/dirty/异源仍停止 |
| symlink | 默认只保存链接文本，不解引用读取目录外；内部相对链接仅在映射后仍指批准包内同一目标时保留。外部/绝对链接、悬空链接作为不激活的 manifest 条目留原地，快照记录文本，legacy 阅读包不创建活跃外链；不复制目标内容 |
| 循环链接、特殊文件、大小写/Unicode 归一化碰撞、路径穿越 | 规划失败零写入，不跳过后宣称完整复制 |

外部 Skill 链接“保留原地、记录文本、未导入/未激活”须在批准清单与完成报告逐项列出；不能把它们的目标算已复制或已审查。若这些排除使 §3.2 的有效链接新失效，则本次安装阻断，需用户另作具体文件处置，不能暗中放宽默认。目录内相对链接也不允许 escape 后重新进入来规避边界。复制后的目录权限不得扩大源可见性；私密文件不得将原文写入公开验收证据。

### 3.4 导入 manifest 与重试

`R/backups/v0-<op>/import-manifest.json` 必填：manifest schema、产品 ID、op、批准引用/时间/计划总指纹、源根与源快照/清单总指纹、目标根、排除清单；逐项 `source_relative_path/type/mode/size/sha256_or_link_text_hash`、目标绝对路径、before 类型/指纹、预期 after、处置（copy/reuse/legacy_index/excluded/conflict）、完成观察；快照完成标记、导入状态与最终 registry 指纹。未知字段/版本/重复键拒绝恢复。

状态为 `prepared → snapshot_complete → applying → outputs_verified → committed`，失败转 `recovery_required` 或 `rolled_back`。状态更新原子写；每次变更先持久化 intent，再写、读回、记结果。`committed` 只在 V 最后原子提交并读回后记；V 内 `legacy_import` 保存 op、source 总指纹、manifest 路径与逻辑完成结果。V 已提交但 manifest 尚未标 committed，属于可明确补全的中断，不再导入。

重试绝不另造 op 重新复制：普通入口停止；显式恢复载入同一 op，验证快照/批准、各路径属于 before/after 二者之一，才选择继续同计划或逆序回滚。第三种字节、缺损快照或身份变化立即停。成功后同版重装只读 V 的一次导入结果，不重新扫描/复制 v0；故意删除 V 也会被快照/manifest/代码痕迹挡住。

## 4. B3：独立入口、获取与零前置

公开入口为根 `INSTALL.md` 和 `python3 -B <已核验源>/scripts/install.py`；不增加第四个 `agm.py` 子命令，不要求 cwd 是 Git 项目、旧工具/Keeper/产品 Skill 已装。安装器内部调用共享 layout/指纹/事务/台账内核，不调用项目 enable 来绕出机器安装。项目三命令遇未安装只诊断并给出此入口，不隐式安装/升级；check 始终只读。

安装器 CLI 合同：无批准运行只输出计划；`--approval-file <绝对路径>` 执行与该计划完全匹配的操作；`--agent` 可重复选择；`--recover <manifest绝对路径> --approval-file ...` 是独立恢复模式，不能与普通安装混用。批准 envelope 使用独立机器 schema=1，不伪造项目键，必含 command、op、R/C/V、来源与提交/清单、通道、三版本、请求/有效执行器、现场观察总指纹、精确 changes、快照/备份/暂存路径、旧账/证据映射、v0 身份确认（无则 null）、confirmed_at/reference。写前锁内重核；变化超出计划即停止重新预览。批准文件只是既有确认的承载，不是自证授权。

“零前置”定义为无本产品/v0/Keeper/项目配置前置。Python≥3.9、Git（采用 Git 获取或验证时）、受支持 macOS 是明确系统前置（2026-10-30 用户确认：已有 Python≥3.9 与 Git 为前提，缺失只说明安装步骤）。缺 Python 时由执行安装的 Agent/用户先诊断，Python 安装器本身不能诊断未能启动的解释器；缺 Git 时输出手动安装/提供已核验本地源的路径。只给引导，不静默安装系统依赖，不远程管道执行脚本。缺任一必要运行时则本次未完成，不宣称完全零系统前置。

来源固定官方仓库 `https://github.com/vincent4j/agent-group-memory` 或用户明确提供的已核验本地 checkout；获取发生在用户已请求安装之后，先固定一次提交和产品代码版本/清单，后续不浮动跟随 HEAD。禁止 reset/pull 改 dirty checkout。获取/暂存目录必须在批准/请求涵盖范围，并由 bootstrap manifest 追踪；普通 help/check/规划不 clone。不能为了预览偷偷建缓存；外层获取与安装器零写规划分别报告。网络内容获取仍遵守环境委派边界。

最终唯一活动代码落位 C；外部开发 checkout 只是本次来源，不成为第二个安装源。代码落位记录来源 URL/提交与清单哈希；只读回脚本/SKILL/入口/台账成功才报告静态安装完成。报告必须含 R/C/V、三版本、op/恢复位置、已接入/absent/unknown/未选执行器、复制/排除项、项目装配命令、新会话 runtime pending。部分接入失败报 partial；无 installed 执行器可报告中枢已建/接入待办，不能报“各家已可用”。项目命令例子必须使用显式实际项目根，不把当前安装目录变成项目。

## 5. B4：版本矩阵与升级闭环

### 5.1 版本账与首版支持范围

新 registry schema=2；产品目录结构版=1。`product_id = agent-group-memory`；`installation_id` 首装生成，升级不变；`product_code_version` 使用产品发行 SemVer，另记 source commit/tree 清单；DESIGN v1.6 是文档版本，不写入代码版本充数。M2/M3 schema=1 没有这些字段，迁移显式记其来源为 `m2-schema1`，不猜历史发行号。

| 源状态 | M4 首个发行代码（记作 T）的行为 |
|---|---|
| 空 / 获批 v0 | 创建 `(schema=2, structure=1, code=T)`；v0 为一次内容导入，不是 schema 升级 |
| 已核验 M2/M3 schema=1 | 严格验证旧 schema → schema=2 + structure=1 + code=T；只迁已知主 checkout 及原授权；执行 §6 |
| 已完成 `(2,1,T)` 且 commit/清单一致 | 幂等；无变更零写；合法已选接入缺口可另做事务 |
| 已完成 `(2,1,P)`，P 为 T 发行转换清单列出的前驱代码 | 更新受管代码/机制与代码版本，不改用户内容；schema/structure 可不变 |
| 任一更高 schema/structure/code 或未知前驱/不可验证来源 | 零写入拒绝；不自动降级或直接视作 P |

M4-07 必须交付可运行前驱 P→T，不只预留函数：从同一批准开发链冻结一个真实可运行的前驱代码快照（独立代码 SemVer/commit/清单），先通过安装器安装 P 形成完成台账，再安装 T。P 与 T 不能仅伪造台账版本差异或替换字符串；至少使用不同的实际受管代码清单，并跑代码替换、读回、最后记账及故障恢复。T 的转换清单必须将 P 的精确三版本/代码清单列为白名单；具体构建提交由发布产物产生并固化，不允许实现按大小比较后任意升级。M2/M3→T 与 P→T 两条均属首版必测闭环，未知未来版始终拒绝。

新 registry 顶层保留原 `projects`、`shared_objects`，增加独立 `product`、`machine`、`migration`、`legacy_import`；这些与 `schema_version` 均必填、无则显式 null/空映射，禁止宽松未知字段。product 包含身份、三版本、源码/清单、完成状态、最后提交 op；machine 包含执行器事实与机器对象，不借项目消费者登记。所有逐字段类型、引用和单元变更需由 M4-02 严格 schema 校验；不放宽旧 schema=1 验证器。

### 5.2 受管代码更新

“用户内容不动”包括用户主题、references、其他 Skills、mcp 及项目记录库；不含有可信安装来源/清单的 C 和产品自身受管入口。受管代码 dirty、异源、额外未归属文件、类型变化或受管块漂移先停，不强制批准覆盖。Git 目录、未跟踪文件与原有开发工作都需保全；不能拿“产品代码可换”覆盖独立用户 checkout。

获批升级在外置 bootstrap 目录先准备完整新代码，核验语法/所需文件/清单及目标版本，再备份完整旧代码。执行安装器自身、恢复脚本及依赖的标准库内核必须复制到同一固定 op 工具包，指纹纳入计划；切换 C 时不再从 C 动态 import。恢复来源是该工具包与旧代码 before 树，不能依赖已被替换或半替换的安装器。

代码替换复用逐文件事务：完整旧代码归档于 `R/backups/upgrade-<op>/code-before/`，对产品清单内每个代码文件原子替换/删除并读回，每项先落 intent；C 根及其 `scripts/` 目录不整体 rename，尤其不搬动仍持有的旧锁、tombstone 和旧恢复材料目录。代码可能短暂混版，因此切换期间由安装标记和持锁阻断新命令，旧命令由 §6 的锁/tombstone 阻断；恢复只用外置工具包。清单更新不把运行态 tombstone 算代码漂移，不删除未归属文件来凑清单。完成全部代码和受管对象验证之后才原子提交 V；然后写提交收尾。升级不运行被导入的 Skills 或旧脚本，不宣称多文件切换原子。

### 5.3 崩溃恢复协议

恢复预览必须先确认 op、主机目标、计划/工具包/全部备份哈希、锁所有者已经退出、V 是否匹配 before/after。显式获批才允许处置已证明失效的锁；不自动偷锁。锁顺序沿 §6。

- V 为 before，且输出仅为 before/after：可继续同一已批准计划，或按逆序恢复 before；继续前复核来源固定清单，不重新下载浮动版本。
- V 为 after，输出全为 after，仅收尾未完成：只补 manifest/锁移交收尾，不重复导入或再执行转换。
- V 为 after、输出混合，或任一路径出现第三种状态/坏备份：停止人工恢复，不猜测成功、不用 after 台账掩盖损坏。
- 回滚恢复旧代码、旧账/旧锁布局、受管入口及对应指纹；不能恢复时留下 `recovery_required` 与必要材料，不假报回滚成功。只删除本次新建且仍空目录，不删除 v0 原件/用户文件。

提交后用户主动“退回旧发行”不属于崩溃恢复，也不受此合同授权；本期无常规降级功能。快照与恢复材料保留，90 天仅提醒清理，不自动删除。【其中“本期无常规降级功能”已被 §12 替代，另受 §25—§26 限定，2026-10-30】

## 6. B5：旧账、恢复材料、锁与写者移交

### 6.1 唯一布局与保真

三项目命令和安装器共用 layout：活动 V、`R/var/.agm.lock`（全产品写锁）、`R/var/.agm.lock/transaction`（既有事务内锁）、`R/backups/`。无 V/未完成安装时写命令不自建空账。check 可以内存观察，不修复机器身份。旧 `scripts/registry.json` 只作明确迁移输入/只读诊断，不能作为新代码活动 fallback。

迁移完整保留 `projects`/checkout 键与授权 yes/no/null、authorization_evidence、provider/store 实际路径和批准、四态、agent 清单、ownership、指纹、original_existed、consumer 双向关系、runtime 状态及证据。事实与 runtime 不因迁移升格，旧 reused 不变 created。若生命周期转换需新增 schema v2 字段，新增的是策略/历史映射，原证据可回溯；不得改旧事实填默认 ready。

所有旧账原始字节、来源路径/代码身份/总指纹以及引用的 manifest、before 文件、代码恢复材料先复制并核验到 `R/backups/m2-migration-<op>/`。原 manifest 按原字节存档；其绝对输出路径不能简单批量替换后直接调用旧恢复函数。对语义等价迁移建立 `reference_map`：原绝对路径→档案路径/哈希/类型；`backup_manifest` 在新账中可改为核验后的新绝对路径，同时显式保存原值和映射。自由文本 evidence 保留原文，解析器通过 reference_map 查档案，不盲改字符串。无法复制/定位的 required created 证据阻断迁移，不降级所有权来通关。历史外部证据文件只复制到私有本机档案，不写公开仓库。

旧 manifest 的恢复目标若包含旧 scripts 台账，使用迁移适配层先核对其历史 before/after 与 reference_map，再按“回滚本次迁移”或“恢复历史项目事务”的明确计划确定活动台账；不能让旧恢复入口穿透 tombstone 再造旧账。其他历史项目路径仍按原批准边界恢复。新账严格校验映射与 required 文件哈希，不能把所有对象指针都改成本次空 manifest。

### 6.2 双账处置

| 现场 | 处置 |
|---|---|
| 只有有效旧账 | 升级迁移候选，按锁协议转 V |
| 只有有效完成 V | 使用 V；其他位置如有 tombstone 必须匹配迁移记录 |
| 两份普通账都存在，无本次可信 migration journal | 无论看似同值或 mtime 先后，零写入停，不能猜赢家 |
| 两账属于同一可信未完成迁移、旧账哈希等于 recorded before、新账等于 recorded after | 普通入口停止；显式恢复完成移交或回滚 |
| 任一不同值、旧账提交后又改变、产品安装 ID 不同 | 冲突停止，保留两份，不合并授权/消费者 |
| V + 匹配 tombstone | 单一活动账，tombstone 不是第二份 registry，不作回退 |

### 6.3 锁顺序与旧写者硬阻断

单靠新版拒读 schema v1 无法停旧写者：当前旧 enable 会把坏普通文件重建为空账，因此**不能只留一个 schema=2 JSON 或说明文件冒充停用**。

统一锁顺序为：`H/.agents-group-install.lock`（机器安装/恢复互斥）→ 旧源 `scripts/.agm.lock`（多来源时规范绝对路径排序）→ 新 `R/var/.agm.lock` → transaction 子锁；释放逆序。常规新项目写者只拿新锁，不反向申请旧/安装锁；常规旧写者沿用旧锁。只读命令不拿任何锁。外置安装锁及 op 目录仅在获批写入阶段创建，R/var 尚无时先创建批准的目录再拿新锁；其 intent 已在 bootstrap journal 中。

具体移交顺序：

1. 明确旧来源清单、暂停旧管理/同步写者，检查所有已知旧锁；旧锁已存在即停止，不能抢占。获批后按顺序取得锁，重核旧账/代码/来源清单。未确认的其他旧写者不能承诺被防住，发现即停。
2. 归档旧账、恢复依赖及原路径映射，核验新账转换；备份旧 registry before 字节。
3. 在仍持旧锁时，将每个旧 `scripts/registry.json` 文件替换为**非空真实目录 tombstone**，内含只读 `redirect.json`（product ID、op、原账哈希、目标 V、迁移状态）。目录替换的每个步骤先记 intent，可恢复。旧版 `read_snapshot` 对非文件节点报 `path_conflict`，既不会走 absent 空账，也不会走坏普通文件重建；普通文件原子替换不能覆盖非空目录。此边界须用真实旧代码夹具验证，不改上游或旧管理器源码。
4. 持有新锁完成代码/受管机制/迁移材料验证，V **最后**原子提交；迁移完整记录 tombstone 路径与哈希、旧源 before、新账 after、reference_map。收尾标 committed 后才释放锁。
5. 中断发生在 tombstone 后而 V 前：普通新旧写者均失败；显式恢复按 journal 恢复旧普通账并回滚，或继续完成 V。只有确认旧进程退出后才释放遗留旧锁。V 后中断按 §5.3 收尾。不能为恢复先删 tombstone 再让旧代码运行。

旧源码之外的任意人为复制版本无法被修改原路径的机制全局禁用；本合同支持“来源清单内、无活跃写者、所有旧账位置均已封堵”的迁移，不宣称系统级阻止任意脚本写盘。若旧源码/账本目录只读、tombstone 无法落位或仍有未受控旧写者，迁移阻断，不能仅迁新 V 后留下可写旧账。C 内及外部旧来源的 tombstone 均持续保留，代码换版不移走它们；活动新代码只用 V，不自动清理旧门禁。

## 7. B6：执行器安装事实与接入集

### 7.1 三态信号

本期仅定义本地静态安装事实，不等同已登录、订阅、模型可用或新会话已读入口。不启动应用、不发模型请求、不读凭据/会话/Cookie。探测限制在当前 PATH、标准应用目录 `/Applications` 与 `H/Applications`、及用户明确提供的可执行文件/应用路径。路径表须分开定义用户 Skill 根和项目 Skill 根。

| 执行器 | installed 的充分信号（至少一条完整成立） | absent | unknown |
|---|---|---|---|
| Codex | PATH 的 `codex` 可解析到可读且可执行的真实包入口，最近包 `package.json` 的 name 精确为 `@openai/codex`，版本非空、对应入口/平台二进制存在；或标准目录 `Codex.app` 的 Info.plist 产品名为 Codex、CFBundleExecutable 存在可执行、bundle 标识非空且签名静态校验一致 | 所有支持候选均可检查且不存在，同时无 hint | 仅 ~/.codex/配置/历史/投影；断链接；未知包装脚本/自编译或原生裸二进制无法识别来源；候选验证失败/权限错误 |
| Claude Code | PATH 的 `claude` 解析到可读可执行包入口，包 name 精确为 `@anthropic-ai/claude-code`，版本非空且入口存在；原生安装可用用户显式提供的本地安装收据+发行文件清单，产品必须明确为 Claude Code、清单哈希与可执行文件一致 | 同左范围全部不存在且无 hint | 仅 ~/.claude；Claude 桌面应用不等于 Claude Code；未知 shell 别名/包装器、无可核验收据的独立二进制、探测错误 |
| WorkBuddy | 标准目录或用户提供的 `WorkBuddy.app`：Info.plist 产品名 WorkBuddy、bundle 标识/版本非空、CFBundleExecutable 所指真实文件可执行、静态签名验证且签名 identifier 与 plist 一致 | 支持目录均可检查、应用不存在且无 hint | 仅 ~/.workbuddy/残留 MEMORY/Skill 投影；只有启动快捷方式、无效/不完整 app、签名/权限/身份矛盾 |

应用签名校验使用系统静态校验命令，不能启动 App 或触发联网/持久缓存；未具备可保证只读的校验后端时返回 unknown。元数据/包名与路径一致性是安装事实依据，不承诺供应链安全审计。原生 Claude 收据必须来自用户明确提供且已核验的安装来源，不能让用户口头“装过”替代文件清单。

规则优先级：有一条完整有效候选且没有与之矛盾的实际身份可 installed；同一候选内部矛盾或多候选无法确定活动来源为 unknown。没有强信号但有 hint 一律 unknown；只有所有支持位置都成功检查且全无候选/hint 才 absent。自定义路径/非支持分发形式不猜 absent，可由用户给出实际路径后重验，不能无限扩扫描。静态读取的事实记录绝对路径、类型、包/bundle 名、版本、可执行文件/元数据哈希、观察时间、探测规则版本；不记录凭据。

### 7.2 默认、显式与路径

- 省略 `--agent`：requested 为支持三家，effective 为 requested∩installed；absent/unknown 只报告，不建用户目录、入口、Skill 或项目桥接。没有 effective 时不伪造三家就绪。
- 显式 `--agent X`：X installed 才进入计划；X absent/unknown 则整个请求在写入前停止，列所缺证据/下一步，不悄悄跳过 X 后报完成。即便用户说“就写这家”也不能绕过本合同；先提供安装证据或安装该执行器再重验。
