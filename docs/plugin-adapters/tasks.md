## 执行规则与依赖图

只有用户批准相应阶段后才执行。任务建议角色不代表已调度 Agent。巴克队长负责方案和阶段验收，章教授负责所有新增网页核查；常规实现可建议 GLM，内核与发行实现可建议突突兔，独立代码审核可建议呱唧，最终由主 Agent 决定。子 Agent 不提交推送。

每项任务开始前读 design、所列源码/官方参考及实际 AGENTS；输出变更清单、可复查证据、失败状态和剩余 pending。禁止复制业务逻辑、使用未证实 API、把合成 HOME 当真实会话。CK 日志由主 Agent 单点整合。

```text
PA-00 文档与合同冻结
  ├─ PA-01 两宿主最小交互/进程验证
  ├─ PA-02 发行载荷与统一身份验证
  └─ PA-03 Python/Git 依赖验证
             ↓ G1：三个门槛均有结论，用户批准实现
PA-04 发行生成与可信 export ── PA-05 机器安装编排/并发
PA-06 公共 Node 依赖与进程适配（与 PA-04 可并行）
             ↓ 冻结协议
       ┌─ PA-07 Paseo 适配
       └─ PA-08 Orca 适配
PA-09 CK 可选安装与 provider 验证（依赖 PA-05/06，宿主接线依赖 PA-07/08）
             ↓ G2：实现审查通过，授权隔离真机验收
PA-10 端到端/恢复/多入口验收
             ↓ G3：验收裁定与发布授权独立
PA-11 发行准备与文档收口
```

同一文件不得多人并行修改。PA-04/05 都涉及 install 与 core，顺序执行；PA-07/08 可并行但只写各自目录。PA-09 不与 PA-05 同时修改安装尾步。所有任务默认不碰真实 HOME、不安装插件；PA-01/03/10 的真机步骤必须在主 Agent 批准的隔离账户/VM/测试宿主进行，方案授权不是这些操作的授权。

## 阶段 0：文档发现与最小验证

### PA-00：补齐允许 API 与支持矩阵

- 依赖：G0，用户批准进入验证；角色建议：巴克队长整理，新增网页由章教授核查。
- 输入：design §2；`/tmp/paseo-plugin-docs/{reference,publishing,hooks}.md`、`/tmp/orca-plugin-docs/{authoring,manifest,catalog,host-api}.md`；官方链接在 design。缓存缺失时由章教授补取。
- 边界：只读资料与验证文档，不改产品/宿主配置。
- 工作：形成带版本、来源、精确签名的 allowed APIs。查 Orca 完整报告展示、确认回调、规范工作区路径、实际 provider/HOME/远程区分；查 Paseo 薄 client 确认组件及 RPC；查宿主固定安装来源可获得信息、非 JS 资产处理、进程限制与最新发行要求。记录官方示例文件及可复用片段，缺失即标缺失。
- 产出：本目录验证记录中列已证实/推断/待测、准确宿主版本、必须拒绝的场景。
- 验收：每个拟用 API 有文档签名；没有编造确认接口、通知 actions、路径字段。新旧文档冲突按最新证据修正；Orca 原生通道不足时可验证用户已接受的一次性确认面板；不扩展为独立管理页面。

### PA-01：两个宿主的最小闭环探针

- 依赖：PA-00；可与 PA-02/03 并行。角色建议：GLM 实现隔离探针、巴克队长核验证据。
- 输入：PA-00 allowed APIs；Paseo 当前 entry/RPC/命令示例；Orca authoring 的 `activate`、`commands.register`、`events.on` 示例。
- 边界：隔离验证目录和测试宿主，不写产品内核，不做真实机器接入。探针仅执行无业务写入的 Python JSON 回显。
- 工作：安装真实子目录插件，验证 Node→Python argv/stdout/错误/取消；在宿主中展示固定文件变更计划、显式确认/拒绝并记录原计划 hash；读取真实规范项目路径与 provider 身份，区分本地主机和远端。不申请 terminal:send 作为确认替代。
- 产出：两个宿主各自操作记录、版本与源 pin、安装目录资产清单、确认和拒绝证据、进程返回值。
- 验收：无需终端；未确认不能执行；通知 delivered 不算批准；工作区名称不能冒充路径；插件 reload/断开确认窗口后旧批准无效；无 Python 时能进入依赖准备说明。Orca 任一关键通道缺失则阻断 PA-08。

### PA-02：生成载荷与 S/R 身份最小验证

- 依赖：PA-00；角色建议：突突兔；不依赖 PA-01/03。
- 输入：`install._managed_source/checkout_source/run`、`user_install._source`、`versions.descriptor/verify`、`upgrade._conversion`、`tests/unit/test_m408_installer.py`；design §4。
- 边界：临时合成仓库、合成 HOME、验证记录。可在夹具中创建测试提交证明 S/R；不得提交项目仓库，不改生产版本与当前 core。
- 工作：按七份文档和 scripts 生成两个完整目录载荷，模拟 S→R，仅 R 加生成物；验证根 Git 入口与插件 export 获得同一内核身份、库存内容。设计窄范围 release-aware 解析契约，给出现有 source-manifest 调用形状与恢复源持久性。
- 产出：确定性 manifest 草案、文件集合、生成差异、源码/发行 pin 分工、普通安装兼容性说明、最小试验结果。
- 验收：无父目录依赖；重生成零差异；S/R 受管字节相同；不需要把 R 写进生成物自身；正常 dirty checkout 仍拒绝；篡改清单/文件/来源、同版异内容被拒绝；两个入口不触发错误的同版替换或库存 marker 冲突。若无法保持现行普通安装语义，停下来修订方案，不放宽 pin/clean。

### PA-03：私有 Python/Git 的可交付性验证

- 依赖：PA-00；角色建议：章教授核查发行来源与许可证，突突兔做隔离运行验证。
- 输入：design §6；`install.run`、`user_install.plan_install`、`project._git`；运行时上游官方发行文档（须章教授补齐，未指定供应者）。
- 边界：临时目录和隔离 macOS，不装 Homebrew/Xcode，不改全局 PATH、不改上游。
- 工作：比较已有解释器复用与固定私有运行时；检查 arm64/x86_64、最低系统、可重定位性、体积、许可/签名、隔离属性、TLS下载与解包。验证真正缺 Python/Git 的环境，不仅修改 PATH 掩盖已有工具。明确 Git 是可验证宿主依赖还是需私有供应包。
- 产出：选定供应者和固定版本/hash/许可证草案、支持矩阵、实测下载大小和启动耗时、风险/维护成本；仍缺证据的架构标 pending。
- 验收：缺 Python 的支持环境只通过宿主批准即可准备并运行；校验失败不执行；用户拒绝无安装；断网可宿主重试；既有依赖离线可用；依赖不在插件可卸载目录。没有可用合法来源则 G1 不通过，不能返回“请自行安装”。

**G1 批准点：** 主 Agent 汇总 PA-01/02/03，运行时联网准备与必要的 Orca 临时确认面板已获产品取舍确认；依据实际验证结论再批准实现，不重复要求用户裁定同一取舍。不能只凭文档通过进入大实现。

## 阶段 1：共用发行与接入机制

### PA-04：实现确定性发行与可信 export

- 依赖：G1、PA-02；角色建议：突突兔。
- 输入：PA-02 冻结清单；现有 `_source`/`checkout_source` 和 installer source-manifest 单测。
- 改动边界：`tools/plugin-release/`、`release/`、统一发行校验模块、`install.py` 窄入口、生成目录、相关 unit/integration tests；不改 CK 上游/业务政策。生成目录由工具输出，不手改。
- 工作：复制原受管文件选择规则的调用方式，复用现有 export 校验；实现根 Git 入口先 clean/pin 再发行归一化、插件绑定已信任发行内容、受控持久 export、S/R 审计字段。生成产物进入同仓发行源，构建步骤不依赖最终用户工具。
- 产出：生成/核验命令与可复现产物、发行合同及失败码、普通安装兼容证据。
- 验收：PA-02 全部负向用例自动化；无重复手写内核；普通安装不引入 Node；不自动改版本、不提交生成发行；生成后产品真源变化使校验失败。

### PA-05：首次接入、复用升级和统一恢复

- 依赖：PA-04；角色建议：突突兔。
- 输入：`install.plan_machine/execute_machine/run`、`user_install`、`upgrade`、`layout`、`transaction`、`enable/remove` 既有批准与锁模式。
- 改动边界：已有安装/发行桥接的必要模块、协议与相关测试；不在 TypeScript 重写任何产品写逻辑，不引入第二台账。
- 工作：结构化输出接入状态；兼容活动内核复用；精确升级/恢复；确认前后绑定活动内核身份；保持锁顺序与已有漂移判定。适配器只是调现有机器 CLI 和项目 CLI，不自定义并行产品安装器。
- 产出：状态转换与 JSON 合同、source/plan/内核身份绑定、恢复入口和持久材料规则。
- 验收：双插件同时首次接入只一次提交；CLI 与插件写冲突拒绝；预览后升级/用户文件变化拒绝旧批准；同版不同内容及未来版不强装；私文、disabled、linked worktree 全保全；旧版无 conversion 不猜升级。中断按现有 journal 恢复，不能自动抢锁。

### PA-06：公共 Node 依赖准备与子进程薄层

- 依赖：G1、PA-03；可与 PA-04 并行，最终与 PA-05 协议对齐。角色建议：GLM。
- 输入：PA-03 固定依赖合同；PA-01 宿主进程探针；design §5～8。
- 改动边界：`plugins/shared` 真源、两插件生成公共模块、Node 测试；不改 Python 产品政策。
- 工作：依赖同意后下载、校验、安全解包、原子就绪；无 shell argv 调用；限制输出、错误转译、操作 ID、取消与未知退出处理。稳定来源/运行时目录供两个插件和普通内核使用；插件目录不持有唯一恢复副本。
- 产出：最小共同调用接口、工具就绪记录和锁、可核验依赖供应清单。
- 验收：路径空格/中文、输出异常、超时、取消、下载篡改、压缩路径逃逸、两宿主竞争、离线复用；仅工具资产写入自身目录；不窃取业务锁；不打印凭据和无关私文。

## 阶段 2：宿主入口与 CK 可选尾步

### PA-07：Paseo 适配

- 依赖：PA-01/04/05/06 协议冻结；角色建议：GLM。
- 输入：PA-00 确认过的 client/server/RPC、命令和 `addHook` 文档片段；design §8/9。
- 改动边界：`plugins/paseo` 手写入口、测试与概览；共享模块只通过 PA-06 集成。
- 工作：首次启用接入流程、命令/报告/精确确认、异常恢复；首版只读事件提示，明确最低宿主版本。无独立管理页面。
- 产出：manifest、薄 client/server、发行概览、类型检查和隔离宿主证据。
- 验收：插件单独安装即能在宿主内完成依赖与机器接入；拒绝不写；换 host/HOME/项目失效；无 UI 客户端时等待批准；事件不自动解除 disabled、不代答 permission、不写 linked worktree。

### PA-08：Orca 适配

- 依赖：PA-01 的 Orca 门槛通过、PA-04/05/06；可与 PA-07 并行。角色建议：GLM 或另一位获授权实现者。
- 输入：authoring 中 worker 注册/释放模式、manifest/capabilities、catalog source.path；PA-00/01 验证的确认和路径通道。
- 改动边界：`plugins/orca`、隔离验收；不自行添加独立管理页，不改 Orca。
- 工作：命令、首次接入、报告、批准、恢复和取消；`contributes.hooks` 空；事件只检查。仅申请实际使用 capabilities。
- 产出：已构建 main、manifest、目录内完整载荷、自定义 catalog 示例、真实宿主证据。
- 验收：无需终端、无预装 memSharing；完整计划与确认闭环；路径来自实证通道；reload/stop 后订阅清理；不把 notifications.delivered 当同意；不得宣称 Community 自动发现或直接 Git selector 已可用。

### PA-09：Context Keeper 可选安装与加载验证

- 依赖：PA-05/06；宿主接线依赖 PA-07/08。角色建议：突突兔负责内核边界，宿主实现者接线；不改上游。
- 输入：`ck_install.py` 的 PIN、LABELS/ROOTS/RULES、`_durable_source/_source`、`plan_context_keeper/execute_context_keeper/tail`；固定上游 Skill/安装器；design §11。
- 改动边界：产品前置获取/宿主可选尾步、测试与文档；CK 上游零修改，现有 CK 记录库零自动写入。
- 工作：自动复用或经同意获取独立持久固定 pin 源；调用原官方预览和独立批准，目标按实际 provider 确定；不受支持者 skipped，不污染主安装结果。宿主内完成，不要求用户输入 source 路径或开终端。
- 产出：宿主×provider 的静态路径/加载支持矩阵、获取与批准记录、冲突/跳过报告、新会话读回证据。
- 验收：拒绝 CK 主产品仍成功；同 pin 复用、异源冲突不覆盖；无项目/disabled/linked worktree 不自动建库记录；首次 `/context-keeper` 遵上游流程；宿主 hook 不模拟自动保存；插件更新卸载后 Skill 源仍可用。仅文件落位不算真实加载。新 provider 需上游适配时只列待核实，不能传不存在的 flags。

**G2 批准点：** 审查实现、类型检查和合成测试通过后，由主 Agent 请求隔离真机验收范围。用户若只批准某宿主，另一宿主保持 pending，不整体虚报通过。

## 阶段 3：验收与发行准备

### PA-10：多入口真实端到端验收

- 依赖：G2、PA-07/08/09；角色建议：呱唧独立验收、巴克队长裁定；仅经用户授权才实际派工。
- 输入：全部任务产出、现有 unit/integration 套件、宿主最低版本、实际 Git 固定目录发行候选。
- 边界：独立 macOS 用户/VM/测试宿主和明确允许的 fixture；不在真实用户 HOME 迁移。未知原始内容保留，不自动清理全局目录。
- 工作/可观察验收矩阵：
  - 两宿主分别从仅有宿主、无 memSharing/无 Python 的支持环境安装；全过程不要求终端，真实完成依赖准备、机器接入和一次项目操作。
  - 普通安装→两插件；Paseo→Orca→普通 CLI；Orca→Paseo；同版复用、有合法 conversion 的升级、不兼容拒绝、一个旧插件遇到新活动内核。
  - 并发首次接入/升级/项目操作；确认后文件/版本/身份漂移；拒绝、断网、下载损坏、宿主强杀、插件卸载后由另一入口恢复。
  - disabled、linked worktree、非 Git、无项目聊天、已有私文及原有入口均保持政策；重复生命周期事件不产生写入。
  - CK 三层安装/发现/新会话加载与授权项目行为单列；未测 provider 标 pending；不支持标 skipped；不生成空日志。
- 产出：逐场景命令/动作、脱敏前后证据、退出码/JSON、来源身份、pass/fail/pending、故障恢复结果。运行内核相同不等于两个宿主都验收通过。
- 检查：按修改范围运行相关测试，最终执行现有全量 unit 和 integration；两插件类型/构建/manifest 校验。扫描旧 hook、shell 拼命令、伪批准、父目录依赖、重复业务实现；人工复核发现。
- 阶段结论：真实未做一律 pending；失败先修复对应任务并定向重验，不扩大成重写内核。

### PA-11：发行准备与文档收口

- 依赖：PA-10 通过及 G3；角色建议：巴克队长整合，主 Agent 执行最终发布动作。
- 输入：PA-04 生成器、验收矩阵、官方当前发布合同、用户明确批准的产品版本。
