# 安装与原生入口 PRD

## 目标与范围

用户直接使用 GitHub README 的普通安装请求，不依赖维护者给特殊命令。安装器解析可信固定来源，展示实际范围；不以临时源码路径作为长期 Skill 入口。

默认给六家范围内本机确实已安装的 Agent 接入；用户可明确只选部分。CLI、App、目录残留和登录状态是不同事实，不能把空目录当已安装，也不能把无账号当作无法安装文件。

## 安装交互顺序

1. 检查依赖和 Agent，集中展示待安装范围及必要依赖，一次确认。已有明确覆盖范围的授权不重复询问。
2. 静默准备依赖、取得可信来源、安装与接入。遇到未知所有权、漂移或权限阻塞时说明具体问题，不覆盖未知内容。
3. 简报已实际完成的接入名单，自动读取各家用户记忆并展示两块融合方案。未融合不说融合成功。
4. 用户明确选定条目或回复“按默认方案”后，按选定方案直接执行，完成后简报；不再次索取“确认执行”。详细规则见 [融合 PRD](sharing.md)。用户“暂不整理”也可结束这一环节。
5. 公共用户记忆流程结束后，才提出 Context Keeper 安装；不得夹在融合选择和执行中。

## Context Keeper 尾步文案与范围

> 为了让 Agent 在新会话中记住项目进度、决策和经验，接着上次的工作继续，需要另外安装 Context Keeper。
>
> 是否为本机已安装的〈实际检测到的 Agent 名单〉安装？回复“安装”或“跳过”。

名单从六家中本机实际安装者生成，不固定三家，也不限制为本次选择接入 memSharing 者。不写“同作者”。不因同意 memSharing 安装就默认同意这个独立产品；无响应和非交互 EOF 不是同意。

用户同意且实际安装成功后，提醒在需要的项目使用 `/context-keeper`，首次使用按其流程创建记录库。跳过不影响公共用户记忆；失败独立报告，不回滚已成功的 memSharing，也不合报成功。

用户将另行扩展上游至六家；本项目不修改上游源码。目标名单与固定上游版本的实际能力必须分别核实：不能给不支持的旧版本传未支持参数并宣称成功，也不能为了兼容旧三家继续把产品目标名单固定为三家。

## 原生 Skill 与增量安装

每个被选 Agent 安装用户记忆入口及原生 `skills/mem-sharing/SKILL.md` 薄入口，指向持久核心。description 为“多 Agent 记忆共享与融合，给你的每一个 AI Agent 同一份记忆。”。

| Agent | 默认原生 Skill 路径（相对用户 HOME） |
|---|---|
| Codex | `.codex/skills/mem-sharing/SKILL.md` |
| Claude Code | `.claude/skills/mem-sharing/SKILL.md` |
| WorkBuddy | `.workbuddy/skills/mem-sharing/SKILL.md` |
| DeepSeek Harness | `.dsh/skills/mem-sharing/SKILL.md` |
| ZCode | `.zcode/skills/mem-sharing/SKILL.md` |
| OpenCode | `.config/opencode/skills/mem-sharing/SKILL.md` |

同名非受管文件、符号链接、受管内容漂移不得覆盖。自定义根依据支持合同处理，未支持的重定向拒绝；技术保护在执行器与按需 Skill 中，不塞入常驻用户规则。

周一只装 Codex，周二装了 Claude，周三补装 memSharing 给 Claude：复用同一公共中枢，新增 Claude 入口和 Skill；读取其已有私文提出增量融合，不能重新复制已有公共规则或重复创建中枢。公共内容仅在用户选定增量方案后变化。

同版本同范围重复安装返回“已安装，已接入。”；无变更、无额外融合、无额外批准，文件字节与元数据不变。无参入口须能验证已有可信来源；缺失与损坏来源区别处理，不能伪造发行凭据。

## 验收标准

覆盖六家全装、选择子集、后装新 Agent、重复零写、未知同名与链接拒绝、失败恢复、无参入口。安装对话验证顺序与实际输出，不能只查模板字符串。名单与结果一致；文件层成功不冒称客户端实际读取成功。
